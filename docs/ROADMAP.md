# SigEye roadmap

Worked through one turn at a time. A turn is a coherent, shippable unit: it ends with a
green CI run and a release on GitHub.

## How a turn works

1. Pick the first unchecked turn below. **If the last CI run is red, fix that first** and
   do not start a new turn.
2. Build it. Pure, Android-free logic goes in `core/analysis/` (or `core/ble/`,
   `core/wifi/`) with JUnit tests; Compose screens go in `experiments/<name>/`.
3. Register any new experiment in `core/Experiment.kt` (id constant, `Experiment` entry
   with `howTo`/`reading`/`limits`) and route it in `MainActivity.kt`.
4. Commit, push to `main`, wait for CI, fix anything it catches.
5. Tick the turn off here and commit that too.

## House rules

- **Push to main. Always. Never open a branch or a PR.**
- There is **no local JDK or Android SDK** — do not try to run `./gradlew`. GitHub Actions
  runs the tests. Push and read the run.
- Every non-trivial piece of logic gets a pure class in `core/` and real unit tests. A
  screen with logic buried in it cannot be tested and will not be trusted.
- **Be honest about limits.** Every experiment has a `limits` field and most have a
  `DiagnosticsPanel` saying what the thing is actually seeing and why it might be showing
  nothing. An empty screen with no explanation is a bug.
- Randomised MAC addresses defeat most cross-time analysis. Wherever that matters, say so
  rather than quietly producing a confident wrong answer.
- Registry data (OUIs, company IDs, service and characteristic UUIDs, appearance values)
  is **generated by script** into `AssignedNumbers.kt` / `VendorData.kt` / `assets/oui.bin`.
  Never hand-type it; an earlier hand-written table had five wrong entries out of
  twenty-three.
- `KeepScreenOn(active)` is for screens that genuinely must stay open; anything recording
  should be in the service instead.
- Shared components live in `ui/`: `DiagnosticsPanel`, `DeviceActions`, `AlertPicker`,
  `radar/RadarPanel`, `KeepScreenOn`, `ExperimentHeader`, `PermissionGate`.
- Watch for prefix-matching string replaces (`import com.sigeye.ui.Diagnostic` also
  matches `DiagnosticsPanel`) — they have caused duplicate imports twice.
- **Never prune imports by searching the body for the symbol.**
  `androidx.compose.runtime.getValue` and `setValue` are operator imports used implicitly
  by `by`, so they appear nowhere in the text and a naive pruner deletes them, breaking
  every delegated property in the file.
- Long-running recordings live in `core/Recordings.kt` and are driven by `ScanService`, not
  by the screen. A screen reads them and toggles a `ScanService.Mode`; it must not own a
  recorder, or the measurement dies with the composition.

## Turns

- [x] Alerts and motion usability (VIBRATE permission, head start, picker ordering)
- [x] Body Absorption: diagnostics, CSV export, adaptive sector resolution
- [x] Speed Estimator: PassWatcher, shared diagnostics panel
- [x] Discovery: baseline, arrivals, snapshots, snapshot diffing
- [x] Bluetooth Explorer: GATT interrogation with live explainers
- [x] Radar consolidation and preflight settings check
- [x] Surveillance signatures: BLE TPMS, Wi-Fi survey, flock-you OUIs
- [x] Place Profiler: hours-long profiling, fixtures versus traffic
- [x] Forensics: record, filter, history, comparison, cadence
- [x] Travelling Companions: multi-leg convoy detection
- [x] Journey persistence and snapshot legs
- [x] Defeating Randomisation: fingerprinting plus the walk-away test
- [x] **Background service.** Move Forensics, Place Profiler and Travelling Companions
      into `core/ScanService` so they survive the screen going off, rather than relying on
      `KeepScreenOn`. Add `ScanService.Mode` entries, a notification per running mode, and
      a way to reattach the UI to a running recording. This is the difference between a
      thing you can demo and a thing you can leave running.
- [ ] **Doppler Walk.** Use the step counter (`Sensor.TYPE_STEP_COUNTER`) to get true
      distance walked, then solve the log-distance path loss model for the exponent `n`
      from RSSI against real metres. Turns "guess the distance" into a measurement.
- [ ] **Rotational Polarisation.** Roll the phone about its long axis (gyroscope, not
      compass) and chart RSSI against roll angle. Antenna polarisation typically gives
      10-20 dB between aligned and crossed. Reuse the `PolarSweep` spine; the gyroscope
      avoids every calibration problem the compass has.
- [ ] **Channel Congestion.** BLE advertises on channels 37/38/39, which sit in the gaps
      between Wi-Fi 1/6/11. Infer per-channel health from arrival gaps and cross-reference
      the Wi-Fi survey's channel occupancy. Explains *why* a link is bad.
- [ ] **2.4 versus 5 GHz penetration.** Using `WifiScanHub`, compare how the same access
      point's two bands attenuate through walls. 5 GHz loses far more. Needs a dual-band
      AP broadcasting both.
- [ ] **Vulnerability Scan.** Flag insecure things nearby. Directly detectable from what is
      already collected: WEP, open networks, WPS enabled, WPA1, hidden-but-broadcasting
      networks, BLE devices accepting unauthenticated connections, and unencrypted
      telemetry such as the TPMS sensors. Named CVEs need a model *and* a firmware
      version, which only `GattExplorer` can supply and only sometimes — so keep that a
      separate, narrower layer and be explicit about which findings are configuration and
      which are a known-vulnerable build. Research real signature sources; do not invent
      CVE mappings.
- [ ] **Primetime pass.** Home screen organisation, onboarding, export and share
      throughout, README and docs, full regression. Consider removing `continue-on-error`
      from the lint step — it hid a real Android 8 crash for weeks.
